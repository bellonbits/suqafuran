SUQAFURAN — REALTIME ANALYTICS
Full reference: what it is, how it works, and how buyer-seller interactions are tracked.
Last updated: 2026-08-24 (Phase 2: Communication, Hot Listings, Seller Response, deeper funnel)


================================================================
1. WHAT IT IS
================================================================

"Realtime Analytics" is the admin-facing analytics suite in shops-app, reachable
from the admin sidebar. It lives at /admin-dashboard/analytics and six sub-pages,
all sharing the same admin sidebar (DashboardLayout + ADMIN_NAV_ITEMS) and a
horizontal tab strip (AnalyticsTabs) for jumping between the seven pages.

There is no separate analytics pipeline, no Kafka/ETL job, no cron aggregation.
It is 11 raw Postgres tables written to by lightweight POST /track/* endpoints,
and the dashboard pages run live COUNT/GROUP BY SQL against those tables on
each page load and on a 30-60s auto-refresh poll.

3. DATABASE SCHEMA
================================================================

File: backend/app/models/analytics.py

UserSession           Active session tracking (device, IP, page history, clicks)
UserActivity           Generic action log (view_listing, search, purchase, etc.)
                        + drives ConversionFunnel stage updates
ConversionFunnel        Per-user funnel timestamps: signup -> search -> view
                        -> cart -> purchase -> repeat
ItemView                Listing view events (device, IP, time spent, referrer)
ShopView                Shop profile view events (same shape as ItemView)
SearchEvent             Search queries (query text, result count, filters)
ClickEvent              chat / whatsapp / call / favorite / share / review
                        clicks tied to a listing_id and/or shop_id
ConversionFunnelEvent   Stage events: view -> click -> chat -> contact ->
                        transaction
GeographicEvent         City/country/lat-lng per visitor event
UserCohort              Per-user rollup: new/returning, seller/verified,
                        total searches/clicks/chats
DeviceMetric            Hourly/daily device-type buckets
AdminAlert              Alert rule definitions (metric, threshold, comparison)
AlertEvent              Log of triggered alerts (status: triggered /
                        acknowledged / resolved)

5. FRONTEND SERVICES — TWO DIFFERENT TRACKERS, DON'T CONFUSE THEM
================================================================

There are two separate tracking clients in shops-app. Only one of them feeds
the Realtime Analytics dashboard.

  services/analytics.ts        (analyticsService)
    - Query-param based POSTs matching the real backend signatures above.
    - trackItemView / trackShopView / trackSearch / trackClick /
      trackConversion.
    - THIS is what the dashboard reads from (SearchEvent, ClickEvent,
      ItemView, ShopView tables).

  services/analytics-tracking.ts   (analyticsTracker, a global singleton)
    - Auto-fires on every DOM click site-wide, plus scroll depth / time on
      page / page views.
    - Posts JSON bodies to /analytics/track/click and /analytics/track/
      activity, gated to authenticated users only (anonymous browsing is
      NOT tracked by this client).
    - Its trackSearch() writes to UserActivity (via /track/activity), NOT
      to SearchEvent — it does NOT feed the Top Searches panel.
    - Its global click payload shape (element_id, x, y, page_width, ...)
      does not match either /track/click endpoint's expected schema (see
      Known Issues below) — it silently fails via sendBeacon.
    - Net effect: this tracker is effectively non-functional for anything
      the dashboard shows. It was left untouched.

6. HOW THE PIPELINE WORKS END TO END (Overview page example)
================================================================

  1. Buyer opens a listing -> useTrackItemView() fires on unmount/id-change
     -> POST /analytics/track/item-view -> row in ItemView.
  2. Buyer clicks "Contact Seller" -> analyticsService.trackClick({event_
     type: 'chat', listing_id, shop_id}) -> POST /analytics/track/click ->
     row in ClickEvent (event_type='chat').
  3. Buyer is redirected to /messages -> the REAL chat system takes over
     (Conversation / ConversationMessage / Message tables, separate from
     analytics entirely — see section 7).
  4. Admin opens Realtime Analytics Overview -> frontend calls
     analyticsService.getOverview(days) -> GET /analytics/admin/overview
     -> backend runs live COUNT() queries against ItemView, ShopView,
     SearchEvent, ClickEvent for the selected time window -> JSON returned
     -> React state updated -> auto-refreshes every 60s.

No caching layer, no pre-aggregation. Every dashboard load is a live query.

7. BUYER <-> SELLER INTERACTION — TWO SEPARATE SYSTEMS
================================================================

IMPORTANT: "Are buyers and sellers interacting" has two different answers
depending on which system you mean.

A) THE REAL CHAT/MESSAGING SYSTEM (this is where actual conversations live)
   CORRECTION (2026-08-24): an earlier version of this document named the
   wrong tables here. The real buyer<->seller marketplace chat is:
   Tables:   MarketplaceConversation (buyer_id, seller_id, listing_id,
             status, last_message_at, buyer_unread_count,
             seller_unread_count, message_count) and Message (sender_id,
             receiver_id, listing_id, conversation_id, content, is_read;
             no read_at timestamp — read state is a boolean only).
   Backend:  backend/app/api/api_v1/endpoints/messages.py (buyer/seller
             send + read), backend/app/api/api_v1/endpoints/admin.py
             (admin-only: GET /admin/conversations, /admin/conversations/
             stats, /admin/conversations/{id}, PATCH .../{id} — full
             cross-seller monitor, ~line 2289-2472), chat_ws.py (WebSocket
             delivery/presence only, no DB writes).
   Frontend: MessagesPage.tsx (buyer), SellerMessagesPage.tsx (seller),
             AdminConversationsPage.tsx (admin monitor: list, stats,
             per-thread detail modal, flag/suspend/mark-reviewed actions;
             now also 30s auto-refresh and a ?filter= deep-link param —
             see section 11), AdminDisputesPage.tsx (read-only thread
             viewer scoped to a filed report).
   Status:   Fully functional, independent of analytics. Every real
             message a buyer or seller sends is permanently stored here.
             This is the source of truth for "who is talking to whom."

   NOTE: `Conversation`/`ConversationMessage`
   (backend/app/models/conversation.py, conversations.py endpoints) is a
   SEPARATE, unrelated legacy feature — Suqafuran-as-system messaging a
   user (keyed seller_id/customer_id, no listing_id) — not buyer<->seller
   chat. Don't confuse the two when reading the codebase.

B) THE ANALYTICS "INTENT" COUNTERS on the Realtime Analytics dashboard
   (Chats / WhatsApp / Call / Favorites / Conversion Rate on the Overview
   page, and the seller-rankings "chats"/"conversions" metrics)
   These are NOT counts of real messages. They are counts of ClickEvent
   rows created only when the frontend explicitly calls
   analyticsService.trackClick({event_type: 'chat'|'whatsapp'|'call'|
   'favorite', ...}) at the moment a buyer clicks a specific button.

   AS OF THE ORIGINAL BUILD, THIS WAS NEVER WIRED UP ANYWHERE.
   No Chat/WhatsApp/Call/Favorite button in the actual UI called
   trackClick. Result: those specific dashboard numbers always read 0
   against real traffic, even though real buyer-seller chat was working
   fine underneath.

   THIS HAS SINCE BEEN FIXED (2026-08-24) — see section 8.

9. KNOWN ISSUES STILL OUTSTANDING (not fixed, flagged only)
================================================================

1. Duplicate /track/click endpoint
   backend/app/api/api_v1/endpoints/analytics_tracking.py defines its own
   POST /track/click that instantiates ClickEvent with fields that don't
   exist on the model (element_id, x, y, page_width, etc. instead of
   event_type/listing_id/shop_id). It is mounted under the same /analytics
   prefix AFTER the correct one in analytics.py (api.py lines 82-83), so
   FastAPI's first-registered-route-wins behavior means this duplicate is
   dead code today — but it's confusing and would break if route
   registration order ever changes.

2. Global raw click tracker (analytics-tracking.ts) is non-functional
   Fires navigator.sendBeacon on every DOM click site-wide with a payload
   shape that matches neither working /track/click schema, and is gated
   to logged-in users only. It doesn't feed any dashboard panel. Left
   as-is since nothing currently depends on it working.

3. Google Maps API key
   The real key now in shops-app/.env is a live key — make sure billing/
   quotas on that Google Cloud project are configured before Geographic
   Analytics gets real traffic, since the map will now actually call the
   Maps JS API.

4. No historical retention/rollup policy
   All raw event tables (ItemView, ShopView, SearchEvent, ClickEvent,
   GeographicEvent, etc.) grow unbounded — there is no archiving or
   downsampling job. At high traffic volumes the live COUNT/GROUP BY
   queries on the dashboard will get slower over time unless indexes are
   monitored or a rollup job is added later.

Backend — new endpoints in backend/app/api/api_v1/endpoints/analytics.py
(same is_admin-guarded pattern as every existing endpoint in that file):

  GET /analytics/admin/communication-overview?days=
    active_conversations (MarketplaceConversation, status not closed/
    suspended, last_message_at within 24h), new_conversations, messages_

    seller's conversations with >=1 seller-sent Message), avg_response_
    seconds (same walk-the-messages technique as above, grouped by
    seller), unanswered (seller_unread_count > 0 count). Ranked by
    response_rate desc.

    %_change vs the prior window.

12. POST-PHASE-2 FIXES (2026-08-24)
================================================================

1. Response-time window-scoping bug (self-review catch, before any user
   report)
   get_communication_overview and get_seller_response_analytics
   (backend/app/api/api_v1/endpoints/analytics.py) were pulling in
   MarketplaceConversation rows filtered by created_at >= cutoff_date
   (conversation STARTED in the window) instead of last_message_at >=
   cutoff_date (conversation ACTIVE in the window) — inconsistent with
   how active_conversations/unanswered_conversations are already scoped,
   and would silently exclude older-but-still-active threads from the
   response-time and per-seller stats. Both changed to filter on
   last_message_at.

2. Grey empty space below short pages
   Every analytics page's content wrapper had `min-h-screen` dropped when
   it was wrapped in DashboardLayout earlier (to avoid double-viewport-
   height nesting), but that left a mismatched-grey gap below any page
   shorter than the viewport — DashboardLayout's own root background
   (#F3F4F8) showing through below the page's own bg-slate-50 wrapper,
   which ends exactly at the content height. Fixed by restoring
   min-h-screen on the outer wrapper `<div>` in all 7 analytics pages
   (AdminAnalyticsMainPage/Users/Sellers/Devices/Geographic/Alerts/
   CommunicationPage.tsx). Confirmed via screenshot the empty-state
   panels themselves (e.g. "Tracking Funnel Initialized", "No listing
   activity in the last 24 hours yet") are correct, expected behavior for
   an environment with no real traffic yet — not a bug.

3. Category Performance showing raw numbers instead of names
   GET /analytics/admin/category-analytics only ever returned
   category_id, never a name — the Overview page's Category Performance
   table rendered "#3", "#7", etc. with no way to know what category that
   was. Fixed by outer-joining Listing.category_id against Category in
   the same query (backend/app/models/listing.py has both models) and
   returning category_name (falling back to "Category #{id}" only if the
   category itself was deleted). Frontend (AdminAnalyticsMainPage.tsx)
   updated to render category_name; table header changed from
   "Category ID" to "Category". Every other panel in the suite already
   showed names/titles as the primary label (Hot Listings, Seller
   Rankings, Seller Response Analytics, Top Searches, Top Users,
   Devices, Geographic) — this was the only remaining digits-only
   display.
